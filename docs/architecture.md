# Architecture

```
┌──────────── frontend (React + TS, Vite) ────────────┐        ┌──────────── backend (Rust) ─────────────────────────────┐
│ ImportPanel → useReviewJob (submit/poll/cancel)     │  HTTP  │ review-server (axum)                                    │
│ ReviewScreen: Board · EvalBar · MovePanel · List    │ ─────▶ │  api/      routes, DTOs, JSON errors                    │
│               Summary · EvalGraph                   │  JSON  │  jobs.rs   queue, progress, cancel, retention           │
│ api/generated/*.ts  ◀── ts-rs (types from Rust)     │        │  pgn.rs    pgn-reader + shakmaty → ParsedGame           │
└─────────────────────────────────────────────────────┘        │  analysis/ pipeline, detectors, explanations            │
                                                               │  engine/   Evaluator trait · UCI process · pool + LRU   │
                                                               │  openings.rs  CC0 opening positions (Book)              │
                                                               │                       │ uses                            │
                                                               │ review-core (no I/O): value · expected_points ·         │
                                                               │   classification · caps2 · summary · config             │
                                                               └───────────────────────┬─────────────────────────────────┘
                                                                                       │ UCI over stdin/stdout
                                                                                 Stockfish process(es)
```

## Principles

- **The recovered rules are isolated.** `review-core` takes plain numbers and facts (`MoveFacts`,
  `Caps2Move`) and returns classifications and scores. It has no engine, board or I/O dependency, and
  every recovered constant is unit-tested there. Changing a rule never touches the engine or the API.
- **The engine is separate from the rules.** The pipeline depends only on the `Evaluator` trait.
  - `EnginePool` implements it with Stockfish.
  - The test suite uses a deterministic one-ply `FakeEngine`.
  - Either can be swapped without changing the review logic.
- **Perspective.** Scores cross the API as White-relative `Eval`. Classification converts to the
  reference engine's mover-relative `Value` encoding in one place (`Value::after_move`), so the
  recovered rules are expressed exactly as recovered.
- **The frontend is a renderer.** It never decides chess facts about the game. Positions, FENs of
  line previews, expected points for the bar and graph, and predicates such as `show_best_move` all
  come from the backend. Shared types are generated by ts-rs, so API drift breaks the TypeScript build.
  - **The one exception is exploring.** When the reader plays their own moves in a sideline, the
    frontend decides their legality, SAN and FENs with `chessops` (`frontend/src/lib/chess.ts`).
  - **Its own evaluations.** It also shows its own engine's evaluations there, always labelled as
    such. The engine is a Stockfish WebAssembly build in a Web Worker
    (`frontend/src/lib/engine/`, `docs/explore-mode.md` §5.1, §5.3).
  - **What stays with the backend.** Classifications, accuracy and the coach still come only from the backend.
    - **Sideline moves too.** These are classified by `POST /api/reviews/{id}/judge` on the browser
      engine's lines, through the same facts builder as the review (`analysis/facts.rs`).
    - **No engine search.** The server runs none for them.

## Concurrency and resources

**Engine processes.**
- `ENGINE_POOL_SIZE` processes at most, guarded by a semaphore.
- A process is spawned lazily and reused.
- A process that times out or misbehaves is discarded and replaced.

**Within one review.** Positions are searched in parallel, up to the pool size, with ordered results
(`futures::buffered`).

**Across reviews.** `MAX_CONCURRENT_REVIEWS` run at once; later ones queue.

**Cancellation.**
- A `CancellationToken` per job reaches every search.
- A running search receives `stop` and its `bestmove` is drained, so the process stays reusable.

**Caching.** An LRU cache keyed by (FEN, limit, MultiPV, Chess960) makes repeated reviews and shared
openings cheap.

**Timeouts.** Every search has a hard limit (`ENGINE_SEARCH_TIMEOUT_SECS`). The handshake has a fixed
10 s limit.

**State.** Jobs are held in memory. Nothing is persisted, and no user data is logged beyond review ids
and timings.

## External services

The browser calls two outside services directly, only when the reader asks it to. They are the
public game APIs that list a player's recent games, in `frontend/src/lib/onlineGames.ts`:
- **Chess.com**: `api.chess.com/pub/player/{name}/games/archives`, then up to 3 monthly archives.
- **Lichess**: `lichess.org/api/games/user/{name}` as NDJSON.

Both are anonymous and allow cross-origin requests. The backend is not involved, so the username
never reaches this app's server. The chosen game's PGN then goes through the normal import.

The last site and username are kept in the browser's `localStorage` (`chess-review:online-account`).
The username is also remembered as the reader's own, so their side is preselected.
